# Многопользовательский чат (broadcast) — теория и разбор кода

Сегодня мы пишем две программы — сервер и клиент, — которые вместе образуют чат сразу для нескольких человек. Любой, кто напишет сообщение, должен увидеть его в чате, и это же сообщение должны увидеть все остальные подключённые.

## Что нового сегодня

Раньше сервер мог общаться только с одним клиентом одновременно. Сегодня добавляются два новых понятия:

- **Поток (thread)** — параллельный «поток выполнения» внутри программы. Сервер заводит отдельный поток на каждого подключившегося клиента, чтобы одновременно общаться сразу со всеми, а не по очереди.
- **Блокировка (Lock)** — механизм, который не даёт двум потокам одновременно портить одни и те же данные (у нас это общий список подключённых клиентов).

Если пока звучит абстрактно — это нормально, дальше по ходу разбора кода станет понятно, зачем это нужно на практике.

## Шаг 2. Пишем `server.py`

### 2.1. Импорты и настройки

```python
import socket
import threading

HOST = "127.0.0.1"
PORT = 5555
```

- `socket` — модуль для работы с сетью, `threading` — для работы с потоками.
- `HOST = "127.0.0.1"` — это «сам компьютер» (localhost), сервер и все клиенты будут на одной машине для теста.
- `PORT = 5555` — порт, на котором сервер будет «слушать» подключения. Можно взять почти любое число от 1024 до 65535 — главное, чтобы этот порт не был занят другой программой.

### 2.2. Общий список клиентов и блокировка

```python
clients = []
clients_lock = threading.Lock()
```

Раньше сервер общался с одним клиентом — держал одну переменную `conn`. Теперь клиентов много, и серверу нужно **помнить их всех**, чтобы разослать сообщение каждому. Поэтому заводим список `clients` — туда будем складывать сокет каждого подключившегося.

`clients_lock` — это блокировка. Проблема вот в чём: к серверу одновременно подключаются несколько клиентов, и каждый обслуживается в своём отдельном потоке. Если два потока **одновременно** попробуют изменить список `clients` (один добавляет, другой удаляет) — может произойти путаница, список может повредиться. Блокировка гарантирует: пока один поток работает со списком — остальные ждут своей очереди. Хорошее правило — общие данные между потоками трогать только под блокировкой, даже если ошибку сходу не видно.

### 2.3. Функция рассылки всем (broadcast)

```python
def broadcast(text):
    with clients_lock:
        for conn in clients:
            conn.sendall((text + "\n").encode("utf-8"))
```

`with clients_lock:` — это «захватить блокировку на время работы со списком, а потом автоматически отпустить». Внутри — просто проходимся по всем сокетам в списке и каждому отправляем текст (`\n` в конце — разделитель сообщений, `.encode("utf-8")` — превращаем строку в байты для передачи по сети).

### 2.4. Обработка одного клиента

```python
def handle_client(conn, addr):
    print(f"Подключился клиент {addr}")
    with clients_lock:
        clients.append(conn)

    incoming = conn.makefile("r", encoding="utf-8", newline="\n")
    try:
        for line in incoming:
            text = line.rstrip("\n")
            print(f"{addr}: {text}")
            broadcast(f"{addr}: {text}")
    finally:
        with clients_lock:
            clients.remove(conn)
        conn.close()
        print(f"Клиент {addr} отключился")
```

Разберём по кусочкам:
- Как только клиент подключился — добавляем его сокет в общий список (под блокировкой).
- `conn.makefile(...)` превращает сокет в объект, из которого можно построчно читать текст (как из обычного файла).
- `for line in incoming:` — сервер читает от этого конкретного клиента сообщение за сообщением и сразу рассылает всем через `broadcast`.
- `try/finally` — важная деталь. Если клиент отключится (закроет программу, разорвётся сеть — что угодно), код внутри `try` прервётся с ошибкой. Но что бы ни случилось, код в `finally` **выполнится всегда** — уберёт клиента из списка и закроет соединение. Если этого не сделать, сервер будет пытаться слать сообщения в уже закрытый сокет и упадёт с ошибкой.

### 2.5. Главный цикл сервера

```python
def main():
    server_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server_socket.bind((HOST, PORT))
    server_socket.listen()
    print(f"Сервер слушает {HOST}:{PORT}")

    while True:
        conn, addr = server_socket.accept()
        threading.Thread(target=handle_client, args=(conn, addr), daemon=True).start()


if __name__ == "__main__":
    main()
```

Главное отличие от того, что было бы «в лоб» без потоков: `accept()` теперь в бесконечном цикле `while True`, и как только кто-то подключился — сервер тут же запускает для него **отдельный поток** (`handle_client`) и сразу возвращается к `accept()` ждать следующего клиента. Именно поэтому сервер может обслуживать многих одновременно: он не «застревает» на одном.

`daemon=True` — значит, что эти потоки не помешают программе завершиться при остановке сервера (`Ctrl+C`).

## Подробный разбор: `socket.socket(...)` и `setsockopt(...)`

### `socket.socket(socket.AF_INET, socket.SOCK_STREAM)`

Это создание самого объекта сокета — «трубки», через которую пойдёт общение. У функции два параметра, и оба задают **тип** этой трубки.

**`socket.AF_INET`** — это про адреса: каким «форматом адресов» мы пользуемся.
- `AF_INET` значит IPv4 — обычные адреса вида `127.0.0.1` или `192.168.1.50` (четыре числа через точку). Это самый распространённый вариант.
- Есть ещё, например, `AF_INET6` для IPv6-адресов (более новый и длинный формат) — но сегодня это не нужно.

**`socket.SOCK_STREAM`** — это про то, *как именно* данные передаются. Тут выбор куда важнее:
- `SOCK_STREAM` означает **TCP** — соединение, при котором сначала происходит «рукопожатие» (клиент и сервер договариваются о связи), все данные доставляются **гарантированно** и **в том порядке**, в котором их отправили, а если что-то потерялось по дороге — TCP сам незаметно для нас перешлёт это заново.
- Альтернатива — `SOCK_DGRAM`, это **UDP**: данные летят как отдельные «посылки», без гарантии, что дойдут, и без гарантии порядка. Быстрее, но менее надёжно.

Для чата TCP — единственный разумный выбор: критично, чтобы сообщения не терялись и не перепутывались местами. Если бы сообщения в чате иногда пропадали или приходили не в том порядке, в котором были написаны, — переписка потеряла бы смысл.

Итого: эта строчка говорит — «создай мне сокет, который работает по обычным IPv4-адресам и через надёжное TCP-соединение».

### `server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)`

Это не про то, что за сокет, а про **настройку** уже созданного сокета. `setsockopt` дословно — «set socket option», «установить опцию сокета».

- **`socket.SOL_SOCKET`** — «уровень», на котором применяется опция: это общая настройка сокета, а не что-то специфичное для TCP.
- **`socket.SO_REUSEADDR`** — конкретная опция, «разрешить повторно использовать адрес».
- **`1`** — значение: включить эту опцию (`0` было бы «выключить»).

Зачем она нужна: когда серверная программа завершается (например, остановили `Ctrl+C`), операционная система **не сразу** освобождает порт, который она слушала. Некоторое время (секунды-десятки секунд) порт остаётся в состоянии «ещё не до конца закрыт» — система подстраховывается на случай, если по сети всё ещё идут какие-то последние пакеты этого соединения.

Проблема в том, что если попробовать **запустить сервер заново** на том же порту в этот момент — получим ошибку вроде `OSError: [WinError 10048] Только одно использование адреса сокета обычно разрешено` (на Windows) или `Address already in use` (на Linux/Mac). А во время разработки сервер перезапускается постоянно — после каждого изменения кода. Без `SO_REUSEADDR` пришлось бы либо ждать, либо каждый раз менять порт.

`SO_REUSEADDR` говорит операционной системе: «не считай это проблемой, разреши мне занять этот адрес, даже если предыдущий сокет на нём ещё не полностью «отпущен»». Это чисто удобство для разработки — на сам чат и его логику никак не влияет.

Проверить на практике: закомментировать эту строку (поставить `#` в начале), запустить сервер, остановить его (`Ctrl+C`) и сразу запустить снова — велика вероятность поймать ту самую ошибку. Затем вернуть строку обратно — ошибка пропадёт.

## Шаг 3. Пишем `client.py`

Клиент проще сервера, потому что не обслуживает всех сразу, а общается только с сервером через одно соединение.

### 3.1. Импорты и настройки

```python
import socket
import threading

HOST = "127.0.0.1"
PORT = 5555
```

### 3.2. Функция приёма сообщений

```python
def receive_loop(sock):
    incoming = sock.makefile("r", encoding="utf-8", newline="\n")
    for line in incoming:
        text = line.rstrip("\n")
        print(f"\n{text}\n> ", end="")
```

Зачем клиенту отдельный поток для приёма? Клиенту нужно **одновременно** уметь две вещи — ждать, пока пользователь что-то напечатает в консоли (`input()`), и ждать, пока от сервера придёт новое сообщение (чтение из сокета). Обе эти операции — **блокирующие**: программа буквально «замирает» на этой строчке, пока не случится нужное событие.

Если бы всё было в одном потоке: клиент завис на `input()`, ждёт, пока напечатают что-то, а в это время пришло сообщение от другого пользователя чата — программа его не увидит, потому что занята ожиданием ввода, а не чтением сокета. Решение то же, что и на сервере: разносим эти два дела по разным потокам, они работают параллельно и не мешают друг другу.

Про `print(f"\n{text}\n> ", end="")` — это косметика. Если во время печати своей строки вдруг приходит чужое сообщение, оно печатается на новой строке (`\n{text}`), а потом заново рисуется приглашение `> `, чтобы было видно, что консоль ждёт ввод.

### 3.3. Главная функция

```python
def main():
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.connect((HOST, PORT))
    print("Соединение установлено. Остановить клиента — Ctrl+C.")

    threading.Thread(target=receive_loop, args=(sock,), daemon=True).start()

    while True:
        text = input("> ")
        sock.sendall((text + "\n").encode("utf-8"))


if __name__ == "__main__":
    main()
```

- `socket.socket(socket.AF_INET, socket.SOCK_STREAM)` — создаём сокет так же, как на сервере (тот же смысл параметров, разобранный выше).
- `sock.connect((HOST, PORT))` — разница с сервером. Сервер делал `bind` + `listen` + `accept` — то есть **ждал**, пока кто-то придёт. Клиент, наоборот, сам **идёт** к серверу по конкретному адресу и порту — одна строчка `connect()`, и соединение установлено (если сервер уже запущен и слушает).
- Дальше запускаем поток `receive_loop` — он постоянно слушает сокет и печатает всё, что приходит от сервера.
- Основной цикл: `input("> ")` ждёт, пока напечатают текст, и отправляет его на сервер через `sock.sendall(...)` — та же логика с `+ "\n"` и `.encode("utf-8")`, что уже встречалась.

## Подробный разбор: `sock.sendall(...)`

В строчке `sock.sendall((text + "\n").encode("utf-8"))` на самом деле слиплись три отдельные вещи.

### Зачем `.encode("utf-8")`

Сокет умеет передавать по сети только **байты** — сырые числа от 0 до 255, никакого понятия о «строке» или «тексте» у сети нет. А `text` у нас — обычная Python-строка (`str`). Чтобы её отправить, её нужно сначала превратить в байты — это и делает `.encode("utf-8")`.

`utf-8` — это конкретный способ, каким текст превращается в байты (**кодировка**). Он универсален и умеет кодировать любые символы, включая кириллицу и эмодзи. Если бы отправитель и получатель использовали разные кодировки, получилась бы «кракозябра» вместо текста. Поэтому важно, чтобы и отправитель, и получатель использовали одну и ту же кодировку — у нас везде в проекте это `utf-8`, что на отправке (`encode`), что на приёме (`sock.makefile("r", encoding="utf-8", ...)`).

### Зачем `+ "\n"`

TCP-соединение — это просто **непрерывный поток байтов**, у него нет понятия «вот тут закончилось одно сообщение, тут началось следующее». Если отправить подряд два сообщения, получатель может увидеть их как один слипшийся кусок байт.

Поэтому мы сами придумываем правило (это называется **протокол**): «конец сообщения — это символ перевода строки `\n`». Из-за этого на другой стороне читаем через `makefile(...)` построчно (`for line in incoming`) — оно ищет как раз эти `\n` и режет поток байт на отдельные сообщения. Если забыть добавить `\n` при отправке — получатель просто никогда не дождётся конца строки и «зависнет» в ожидании.

### Зачем `sendall`, а не `send`

У сокета есть два похожих метода:

- **`send(data)`** — пытается отправить данные, но **не гарантирует**, что отправит всё целиком за один раз. Возвращает число — сколько байт реально ушло. Может оказаться, что из 1000 байт ушло только 600, и об оставшихся 400 придётся позаботиться самому — вызвать `send` ещё раз с остатком, и так по кругу, пока всё не уйдёт.
- **`sendall(data)`** — делает это «дозаписывание остатка» за тебя, внутри себя, в цикле. Он либо гарантированно отправляет **все** переданные байты, либо, если что-то пошло не так (например, соединение оборвалось), выбрасывает исключение. Поэтому `sendall` ничего не возвращает (`None`) — раз он либо отправил всё, либо упал с ошибкой, возвращать «сколько отправилось» уже не нужно.

Почему `send` вообще может отправить не всё сразу? У сети и операционной системы есть внутренние буферы ограниченного размера, и если данных много (или сеть перегружена), система может физически не успеть принять весь кусок за один вызов.

В нашем чате сообщения крохотные (одна строка текста), и `send` почти наверняка отправил бы её целиком с первого раза. Но `sendall` — это просто хорошая привычка по умолчанию: она снимает необходимость думать «а вдруг в этот раз отправится не всё» для абсолютно любого объёма данных, и код от этого не усложняется ни на строчку.

Итого вся строчка `sock.sendall((text + "\n").encode("utf-8"))` читается так: «возьми текст, добавь в конец маркер конца сообщения, преврати получившуюся строку в байты — и гарантированно отправь их все целиком».
