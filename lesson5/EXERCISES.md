# Урок 5. Задания на доработку кода

Ниже — подсказки, **не готовый код**. Эталонные решения — в папке [solutions](solutions/README.md). Запуск — из папки урока: `python -m server`, `python -m client`.

Хорошее правило для этого урока: если добавляешь новую команду, сначала **придумай сообщение протокола** (какой `type`, какие поля, кто кому отправляет), а уже потом пиши код.

## Лёгкие

### 1. Команда `/help`

По команде `/help` клиент печатает список доступных команд. На сервер ничего не отправляется.

- Где обрабатываются введённые команды? Добавь ещё одну ветку в `if/elif`.
- Текст справки удобно хранить в константе в начале файла (многострочная строка в тройных кавычках).
- Упомяни `/help` в приветствии клиента.

### 2. Ограничение длины ника

Сервер не пускает ники длиннее 20 символов и отвечает понятной ошибкой.

- Максимальную длину вынеси в `common/config.py` — это настройка.
- Где сервер проверяет ник? Добавь проверку рядом, до записи в `self.clients`.
- Длина строки — функция `len`.

### 3. Сервер не падает от странных сообщений

Если клиент пришлёт сообщение без поля `type` или с неизвестным типом, поток клиента сейчас упадёт с `KeyError`. Сделай так, чтобы сервер записал предупреждение в лог и продолжил работу.

- `msg.get("type")` вместо `msg["type"]`. То же для `text`.
- В цепочку `if/elif` добавь последний `else` с `logger.warning(...)`.
- Чтобы проверить, можно временно отправить из клиента что-нибудь вроде `{"type": "abracadabra"}`.

## Средние

### 4. Команда `/nick` — смена ника

`/nick Вася` — меняет ник на лету, все видят «Аня теперь Вася».

- Придумай сообщение: например, `{"type": "nick", "username": "Вася"}`.
- На сервере: новый ник надо проверить (не пустой, не занят), удалить старый ключ из словаря и добавить новый — всё под **одной** блокировкой.
- Метод словаря `pop(ключ)` удаляет ключ и возвращает значение — удобно «переложить» сокет под новый ключ.
- Переменная `username` используется в `finally` при выходе. Не забудь её обновить — иначе при выходе удалится не тот ник.

### 5. Время в сообщениях

Сервер добавляет к каждому сообщению поле `time` (`"14:05"`), клиент показывает его: `[14:05] Аня: привет`.

- Почему время лучше ставить на сервере, а не на клиенте?
- `datetime.now().strftime("%H:%M")`.
- На клиенте используй `msg.get("time", "")` — вдруг поля нет.

### 6. Честный вход: ждём ответа сервера

Сейчас клиент отправляет `join` и сразу начинает работать, даже если ник занят. Сделай нормальный обмен: сервер отвечает `{"type": "join_ok"}` при успехе, а при ошибке **не закрывает** соединение, а даёт попробовать другой ник.

- На сервере: вместо одного `next(messages)` — цикл по сообщениям, пока не придёт подходящий ник. Сообщение об ошибке — и ждём следующий `join`.
- `join_ok` нужно отправить **до** рассылки «вошёл в чат» — почему это важно для клиента?
- На клиенте: цикл «спросить ник → отправить → `reply = next(messages)` → если `join_ok`, выйти из цикла». Поток приёма запускаем **после** успешного входа и передаём ему **тот же** генератор.

## Посложнее

### 7. Команда `/me`

`/me машет рукой` → все видят `* Аня машет рукой`.

- Новый тип сообщения от клиента, например `action`.
- Сервер может разослать результат как уже существующий тип `system` — тогда клиент менять почти не нужно. Почему это удобно?

### 8. Защита от спама

Сервер не даёт одному пользователю отправить больше 5 сообщений за 10 секунд: лишние не рассылаются, отправитель получает ошибку «Слишком часто».

- Для каждого клиента храни время его последних сообщений. Где хранить, если у каждого клиента свой поток? (Подсказка: локальная переменная внутри `handle_client` — у каждого потока своя.)
- Удобная структура — `collections.deque`: быстро добавлять в конец (`append`) и удалять из начала (`popleft`).
- Время для замеров — `time.monotonic()`: оно не «прыгает», если на компьютере перевели часы.
- Алгоритм: убрать из начала все отметки старше 10 секунд → если осталось 5 и больше — отказ → иначе добавить текущее время и разослать.
- Числа 5 и 10 вынеси в `common/config.py`.
