# Урок 6. База данных: история сообщений — теория и разбор кода

До сих пор всё, что происходило в чате, жило только в оперативной памяти сервера. Остановил сервер — переписка исчезла. Сегодня сервер начинает **сохранять сообщения в базу данных** на диске, а каждому новому участнику при входе показывает последние 20 сообщений.

Что меняется по сравнению с уроком 5:
- новый пакет `db/` с модулем `storage.py` — вся работа с базой;
- `common/config.py` — настройка `HISTORY_LIMIT`;
- `server/core.py` — сохранение сообщений и отправка истории;
- `client/__main__.py` — показ истории.

## Основные понятия

- **База данных (БД)** — программа или файл, который хранит данные упорядоченно и позволяет быстро их искать и менять.
- **SQLite** — база данных, которая живёт в **одном обычном файле** (у нас `chat.db`). Отдельный сервер БД устанавливать не нужно: модуль `sqlite3` встроен в Python.
- **Таблица** — как лист в Excel: заданные **столбцы** (что храним) и много **строк** (записей).
- **SQL** — язык запросов к базе. Четыре главных команды: `CREATE TABLE` (создать таблицу), `INSERT` (добавить строку), `SELECT` (прочитать), `UPDATE`/`DELETE` (изменить/удалить).

Наша таблица `messages`:

| id | from_user | text | created_at |
|---|---|---|---|
| 1 | Аня | привет | 2026-09-27 08:00:04 |
| 2 | Боря | привет, Аня! | 2026-09-27 08:00:11 |

## Шаг 2. `db/storage.py` — работа с базой

Пакет `db` (папка с пустым `__init__.py`) — отдельное место для всего, что касается хранения данных. Остальной код не знает, как именно устроена база: он просто вызывает функции `save_message` и `load_history`.

### 2.1. Путь к файлу базы

```python
import sqlite3
from pathlib import Path

DB_PATH = Path(__file__).resolve().parent.parent / "chat.db"
```

- `sqlite3` — встроенный модуль для SQLite.
- `pathlib.Path` — удобная работа с путями к файлам.
- Разбор `Path(__file__).resolve().parent.parent / "chat.db"` по шагам:
  - `__file__` — путь к текущему файлу, то есть к `db/storage.py`;
  - `.resolve()` — превратить в полный абсолютный путь;
  - `.parent` — папка, где лежит файл: `db/`;
  - ещё `.parent` — папка выше: папка урока;
  - `/ "chat.db"` — оператор `/` у `Path` склеивает пути.
  - Итог: `<папка урока>/chat.db`.

Зачем так сложно, а не просто `"chat.db"`? Просто имя файла ищется относительно **текущей рабочей папки** — откуда запустили программу. Запустишь из другой папки — появится вторая, пустая база. Путь «от файла» не зависит от того, откуда запускали.

### 2.2. Подключение и создание таблицы

```python
def get_connection() -> sqlite3.Connection:
    # check_same_thread=False: соединением пользуются потоки разных клиентов.
    # За то, чтобы два потока не писали одновременно, отвечает ChatServer.lock.
    conn = sqlite3.connect(DB_PATH, check_same_thread=False)
    conn.execute(
        """
        CREATE TABLE IF NOT EXISTS messages (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            from_user TEXT NOT NULL,
            text TEXT NOT NULL,
            created_at TEXT NOT NULL DEFAULT (datetime('now'))
        )
        """
    )
    return conn
```

- `sqlite3.connect(DB_PATH, ...)` — открыть базу. Если файла нет — он будет создан.
- `check_same_thread=False` — по умолчанию `sqlite3` запрещает пользоваться одним соединением из разных потоков (подстраховка от ошибок). У нас каждый клиент обслуживается в своём потоке, и все они пишут в одну базу. Мы снимаем запрет, но берём ответственность на себя: все обращения к базе будем делать под блокировкой сервера.
- `conn.execute("...")` — выполнить SQL-запрос. Тройные кавычки — чтобы записать запрос в несколько строк.

SQL-запрос построчно:
- `CREATE TABLE IF NOT EXISTS messages (...)` — создать таблицу `messages`, **если её ещё нет**. При повторных запусках сервера ничего не сломается и данные не пропадут.
- `id INTEGER PRIMARY KEY AUTOINCREMENT` — номер записи: целое число, **первичный ключ** (уникальный номер строки), который база сама увеличивает на 1 для каждой новой записи.
- `from_user TEXT NOT NULL` — ник автора; `TEXT` — строка, `NOT NULL` — поле обязательно.
- `text TEXT NOT NULL` — текст сообщения.
- `created_at TEXT NOT NULL DEFAULT (datetime('now'))` — время создания. `DEFAULT` — значение по умолчанию: если при вставке время не указали, база подставит текущее. Важно: `datetime('now')` в SQLite — это время **UTC** (по Гринвичу), а не местное.

### 2.3. Сохранение сообщения

```python
def save_message(conn: sqlite3.Connection, from_user: str, text: str) -> None:
    conn.execute("INSERT INTO messages (from_user, text) VALUES (?, ?)", (from_user, text))
    conn.commit()
```

- `INSERT INTO messages (from_user, text) VALUES (?, ?)` — добавить строку, заполнив два столбца. `id` и `created_at` база заполнит сама.
- `?` — **места для параметров**. Сами значения передаются отдельно, кортежем `(from_user, text)`. Почему так — в разборе про SQL-инъекции ниже.
- `conn.commit()` — **зафиксировать** изменения. Пока не вызван `commit`, изменения видны только этому соединению и не записаны на диск окончательно.

### 2.4. Загрузка истории

```python
def load_history(conn: sqlite3.Connection, limit: int) -> list[tuple[str, str, str]]:
    rows = conn.execute(
        "SELECT from_user, text, created_at FROM messages ORDER BY id DESC LIMIT ?",
        (limit,),
    ).fetchall()
    return list(reversed(rows))
```

- `SELECT from_user, text, created_at FROM messages` — прочитать три столбца из таблицы.
- `ORDER BY id DESC` — отсортировать по номеру **по убыванию** (сначала самые новые).
- `LIMIT ?` — взять не больше `limit` строк. Вместе: «последние N сообщений».
- `(limit,)` — параметр кортежем (запятая обязательна: кортеж из одного элемента).
- `.fetchall()` — получить все найденные строки списком кортежей: `[("Боря", "привет, Аня!", "..."), ("Аня", "привет", "...")]`.
- `reversed(rows)` — развернуть: мы брали от новых к старым, а показывать историю нужно от старых к новым, как в любом чате.

## Подробный разбор: SQL-инъекции и знак `?`

Кажется, проще собрать запрос f-строкой:

```python
conn.execute(f"INSERT INTO messages (from_user, text) VALUES ('{from_user}', '{text}')")   # НЕЛЬЗЯ!
```

Но текст сообщения пишет **пользователь**. Если он отправит `I'm here`, апостроф закроет строку раньше времени, и запрос сломается. А злоумышленник может специально подобрать текст так, чтобы он стал **частью SQL-команды** — например, удалить таблицу. Это называется **SQL-инъекция**, одна из самых известных уязвимостей в мире.

С `?` база получает команду и данные **раздельно**: что бы ни было в тексте, оно всегда будет только данными. Правило: **никогда не подставляй пользовательские данные в SQL через f-строки или `+`** — только через параметры.

## Подробный разбор: зачем `commit`

База работает **транзакциями**: несколько изменений можно сделать «пачкой» и применить все разом (`commit`) или отменить все разом (`rollback`). Например, при переводе денег нельзя списать с одного счёта и не зачислить на другой. У нас каждое сообщение — отдельная маленькая транзакция: вставили — сразу зафиксировали. Если забыть `commit`, сообщения будут «видны» текущему серверу, но после перезапуска окажется, что их нет.

## Шаг 3. `server/core.py`

### 3.1. Импорты и подключение к базе

```python
from common.config import HISTORY_LIMIT
from common.protocol import iter_json, send_json
from db.storage import get_connection, load_history, save_message
...
    def __init__(self, host: str, port: int):

        self.clients: dict[str, socket.socket] = {}
        self.lock = threading.Lock()

```

Сервер при создании открывает соединение с базой и хранит его в поле `self.db`. Одно соединение на весь сервер — им пользуются все потоки, под общей блокировкой `self.lock`.

### 3.2. Отправка истории новому участнику

```python
        logger.info("%s подключился (%s)", username, addr)

        with self.lock:
            history = load_history(self.db, HISTORY_LIMIT)
        for from_user, text, created_at in history:
            send_json(conn, {"type": "history", "from": from_user, "text": text, "at": created_at})

        self.broadcast({"type": "system", "text": f"{username} присоединился к чату"})
```

- Читаем историю под блокировкой — чтобы никакой другой поток не писал в базу в этот момент.
- `for from_user, text, created_at in history:` — каждая строка результата — кортеж из трёх значений, и мы сразу раскладываем его по трём переменным.
- Каждое сообщение истории отправляем **только** новому участнику, с новым типом `history`, чтобы клиент мог показать его иначе, чем «живые».
- Отправка (`send_json`) — уже **после** выхода из-под блокировки: держать блокировку во время медленных сетевых операций незачем.
- Историю отправляем **до** рассылки «присоединился» — так на экране сначала прошлое, потом настоящее.

### 3.3. Сохранение каждого сообщения

```python
                if msg["type"] == "message":
                    with self.lock:
                        save_message(self.db, username, msg["text"])
                    self.broadcast({"type": "message", "from": username, "text": msg["text"]})
```

Сначала записываем в базу (под блокировкой), потом рассылаем. Остальной код сервера не изменился.

## Подробный разбор: почему одна блокировка и для клиентов, и для базы

Блокировка защищает **общие данные**, которыми пользуются несколько потоков. У нас их теперь два вида: словарь клиентов и соединение с базой. Можно было бы завести две блокировки, но одна проще и надёжнее: меньше шансов запутаться. Для чата на несколько человек скорости хватит с огромным запасом.

## Как запустить и проверить

1. Из папки урока: `python -m server`, затем пара клиентов `python -m client`.
2. Напиши несколько сообщений.
3. Останови сервер полностью и запусти снова.
4. Подключи нового клиента — он увидит прошлые сообщения с пометкой `[история]`.
5. Рядом с кодом появился файл `chat.db`. Его можно открыть программой **DB Browser for SQLite** или прямо в PyCharm (панель **Database**, если она есть в твоей версии) и посмотреть таблицу `messages`.

## Частые ошибки

- **История пустая после перезапуска** — забыли `conn.commit()`.
- **`ProgrammingError: SQLite objects created in a thread can only be used in that same thread`** — забыли `check_same_thread=False`.
- **Две разные базы** — путь к файлу задан относительно рабочей папки, а сервер запускали из разных мест. Поэтому путь строим от `__file__`.
- **Время в истории «отстаёт» на несколько часов** — `datetime('now')` в SQLite — это UTC, а не местное время.
